# LexRadar: email и Telegram

Заявка `/lexradar` отправляется на `golwebstudio@bk.ru` через существующий SMTP Mail.ru. После принятия письма выполняется один `sendMessage` напрямую в Telegram Bot API. Обе доставки входят в один обработчик; настройки SMTP не меняются. Telegram не заменяет email.

Уведомление содержит имя, email, адрес сайта, заполненные телефон и комментарий, существующий номер заявки и серверную дату поступления в UTC. Дата совпадает с письмом и не берётся из браузера. Передаются только проверенные поля формы; UTM, IP, honeypot, согласие и произвольные поля запроса в Telegram не попадают. Текст отправляется без HTML/Markdown-разметки, предпросмотр ссылок отключён. Максимальные значения формы помещаются в одно сообщение Telegram без обрезки.

Общая форма `/api/lead` сохраняет прежнее уведомление только о статусе. SMTP-диагностика и общий `sendEmail` не вызывают Telegram.

## Развёртывание

1. Подготовить проверенный checkout PR по [DEPLOYMENT](DEPLOYMENT.md), сохранить рабочее окружение и прежний SHA для отката. Node 24, npm 11.9.0, Python 3. Выполнить `npm ci` и `npm run check`. Не запускать `smtp:setup`, не копировать `.env.example` поверх рабочих env-файлов.
2. В личном Telegram открыть **@GolWebStbot** и нажать **Start** (или отправить `/start`). Бот не может начать личный разговор самостоятельно. Входящие сообщения ботом не обрабатываются.
3. В интерактивном SSH-терминале под владельцем файлов приложения, из каталога production checkout выполнить:

   ```sh
   npm run telegram:setup
   ```

   Ввести `НАСТРОИТЬ`, затем токен из BotFather в скрытом приглашении. **Не передавать токен в аргументах команд, истории shell, Git, чате, скриншотах или логах.** Для Chat ID нажать Enter: значение по умолчанию **241367335**. Рабочая отправка читает исключительно серверные `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`; значение по умолчанию используется только установщиком.
4. Установщик сначала сохраняет `TELEGRAM_NOTIFICATIONS_ENABLED=false`. Ввести `ОТПРАВИТЬ`, чтобы выполнить одно контрольное сообщение без заявки, персональных данных и email. Только после фактического получения в личном чате ввести `ПОЛУЧЕНО`: установщик задаст `TELEGRAM_NOTIFICATIONS_ENABLED=true`. При ошибке или пропуске проверки уведомления останутся выключенными.
5. Выполнить безопасные проверки:

   ```sh
   npm run telegram:inspect
   npm run lexradar:inspect
   ```

   Они не отправляют сообщения/письма и не меняют настройки. При исправной конфигурации Telegram показывает `TELEGRAM_ENABLED` и `TELEGRAM_CONFIG_READY`; форма — `FORM_READY` и `FORM_FLAG_ENABLED`. `lexradar:inspect` возвращает код 1 при блокировке или выключенном флаге. Это проверка конфигурации, а не реальной доставки или запущенного PM2-процесса.
6. Применить окружение штатной процедурой существующего production-процесса. В текущей документации указан `pm2 restart golwebstudio --update-env`; сначала проверить имя процесса и источник переменных. Перезапуск сам по себе не очищает старые process overrides. Секреты и `pm2 env/jlist/dump` не публиковать. Не менять SMTP, Nginx и число workers ради Telegram.
7. Открыть `/lexradar` на каноническом домене, проверить доступность формы и согласие. Отправить одну контрольную заявку с пометкой «Тест LexRadar», проверить письмо и Telegram: одинаковые номер/дата и введённые данные. Тестовые контакты должны принадлежать оператору. При неопределённой доставке не повторять заявку вслепую — сначала проверить ящик и номер.

Для отдельного явного контрольного Telegram-теста после настройки:

```sh
npm run telegram:inspect -- --send-test
```

Без флага команда полностью офлайн. С флагом отправляет ровно одно сообщение даже при выключенных уведомлениях; успешный API-ответ не подтверждает получение владельцем.

## Почему было FORM_NOT_READY_CHECK_ORIGIN_AND_ABUSE_CONFIG_FORM_LEFT_DISABLED

Этот код выдаёт SMTP-установщик, когда контрольное письмо уже принято и владелец подтвердил его получение, но `getLexradarConfig().ready` остаётся false. Он намеренно оставляет `LEXRADAR_FORM_ENABLED=false`. Успешный SMTP-тест не подтверждает origin и режим защиты.

Проверка серверных env/PM2 в рамках разработки не выполнялась: конкретный отсутствующий параметр production без доступа к серверу неизвестен. Новая команда `npm run lexradar:inspect` показывает точные блокирующие условия без секретов:

| Код после FORM_BLOCKER_ | Исправление в действующем серверном источнике окружения |
| --- | --- |
| SITE_ORIGIN_MISSING_OR_INVALID | `LEXRADAR_SITE_ORIGIN=https://www.golwebstudio.ru`, без `/lexradar`, query/hash. Он должен совпадать с Origin браузера; домен без www должен штатно перенаправляться на канонический. |
| ABUSE_MODE_MISSING_OR_INVALID | Выбрать режим по реальной топологии: `single-process` только для одного процесса приложения; `edge` — при проверенном общем ingress-limit. Пустое значение из `.env.example` закрывает форму. |
| EDGE_TRUSTED_IP_HEADER_REQUIRED | Проверить, что proxy перезаписывает IP-заголовок и прямой порт Node закрыт; затем задать `LEXRADAR_TRUST_PROXY=true` и `LEXRADAR_CLIENT_IP_HEADER=x-real-ip` (либо поддерживаемый заголовок Vercel на Vercel). |
| EDGE_RATE_LIMIT_NOT_CONFIRMED | Сначала проверить реально действующий общий rate limit, затем `LEXRADAR_EDGE_RATE_LIMIT_CONFIRMED=true`. Один флаг не создаёт защиту. |
| SMTP_CONFIG_INVALID / RECIPIENT_CONFIG_INVALID | Проверить конфликтующие источники/aliases по [ENVIRONMENT](ENVIRONMENT.md). Не заменять рабочие SMTP-значения и не запускать установщик заново ради origin/защиты. |

Исправлять только соответствующие LexRadar-переменные. Для единственного PM2-процесса с консервативным общим bucket допустим `single-process` без доверия IP-заголовкам: лимит 5 попыток за 10 минут общий для посетителей. Не выбирать этот режим при нескольких workers или распределённом запуске.

После `FORM_READY`, ранее подтверждённого email и проверки реальной топологии установить `LEXRADAR_FORM_ENABLED=true` в действующем источнике и повторить инспекцию. Новая SMTP-отправка для исправления этих флагов не требуется. Переменные процесса имеют приоритет над `.env.production.local`, `.env.local`, `.env.production`, `.env`; исправленный файл может быть перекрыт. Не отключать проверку origin, согласие, honeypot или limiter.

## Секреты и сохранность настроек

Установщик меняет только три Telegram-ключа, консолидирует их в `.env.local` с правами 600 и сохраняет остальные строки, включая SMTP и LexRadar. Используется существующий атомарный редактор с проверкой конкурентных изменений и откатом. Дубликаты, process overrides, отслеживаемые Git env-файлы, symlink и неоднозначный синтаксис останавливают настройку. Токен проверяется локальным Next env parser без вывода значения. Установщик не перезапускает сервисы.

Формат token/chat_id проверяется до сети. URL API фиксирован, redirect запрещён. Не включать verbose сетевые логи: Telegram Bot API содержит токен в URL. Логи содержат только фиксированные коды ошибок, без адресов, данных заявки и сырых ответов API.

## Надёжность и откат

- Telegram вызывается после SMTP acceptance, без автоматических повторов, с общим deadline до 1500 ms на сеть и JSON. Обработчик ожидает завершения попытки.
- Timeout, 429, 5xx, `ok:false`, невалидный JSON, отсутствие токена и исключение не меняют успешный `ACCEPTED` и не повторяют email. При неуспешном/неопределённом SMTP уведомление не отправляется.
- Сбой Telegram может привести к потере уведомления. Автоповтора нет, чтобы не дублировать принятое сообщение при потерянном ответе.
- Повторы UUID LexRadar используют существующий cache 30 минут в одном процессе. Рестарт, несколько workers и истечение TTL не обеспечивают exactly-once.
- Для отключения только Telegram задать `TELEGRAM_NOTIFICATIONS_ENABLED=false` в действующем источнике и штатно применить окружение. Email и защита формы продолжают работать. Для отката кода использовать записанный прежний SHA и отдельный подготовленный release-каталог по DEPLOYMENT; не стирать env.

Согласие LexRadar обновлено до `lexradar-2026-10-19-v4`, чтобы отражать передачу полей через Telegram. Старые открытые страницы со старой версией согласия требуют обновления перед отправкой.

## Проверки PR

Тесты используют только синтетические токены/контакты и mock-транспорты: точный состав данных, серверная дата, отсутствие лишних полей, максимальная длина/Unicode, пустые необязательные поля, дедупликация, ошибки Telegram при успешном email, SMTP failure/uncertainty, origin/consent/honeypot/rate limit, диагностика ready и сохранность SMTP/LexRadar установщиком. Реальные production-письма и Telegram в разработке не отправляются. Фактические результаты проверок и ограничения окружения указаны в PR; локальные тесты не подтверждают production-доставку.
