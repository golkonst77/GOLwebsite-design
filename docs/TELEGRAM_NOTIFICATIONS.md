# Telegram-уведомления владельцу

Подготовка к отдельной настройке; **на production этим PR не включены**. Новые Telegram-сообщения и письма при разработке не отправлялись. Рабочая Mail.ru-доставка ранее подтверждена владельцем и не перенастраивается.

## Что делает код

```text
Общая форма → /api/lead → sendLeadEmail → общий sendEmail
                                             ↓ SMTP accepted
                         одна попытка Telegram → прежний ответ API

LexRadar → /api/lexradar → существующий cached delivery Promise
                         → общий sendEmail → SMTP accepted
                         → одна попытка Telegram → прежний ACCEPTED
```

Общий `sendEmail`, SMTP-диагностика и установщик Mail.ru не рассылают Telegram-уведомления. Общая форма использует отдельный маленький адаптер `lib/lead-delivery.ts`; LexRadar вызывает уведомление внутри уже дедуплицированной операции `deliver`.

Уведомление после SMTP содержит только фиксированное название формы, «Письмо принято почтовым сервером», предложение проверить рабочую почту и существующий UUID LexRadar, если он есть. Основной форме новый идентификатор не добавляется. Имя, email, телефон, URL сайта, комментарий, IP, UTM, текст письма и произвольные поля запроса в Telegram не передаются. UUID допускается только в фиксированном UUID-формате.

Telegram не вызывает автоматическую проверку сайтов, ответ клиенту, CRM, меню бота или обработку `/start`. Бот используется только для исходящего `sendMessage` владельцу; webhook/polling, отдельного bot server, базы и очереди нет.

## Серверная конфигурация

| Имя | Правило |
| --- | --- |
| TELEGRAM_NOTIFICATIONS_ENABLED | Только точная строка true включает уведомления; default false |
| TELEGRAM_BOT_TOKEN | Только серверный секрет; пусто в .env.example |
| TELEGRAM_CHAT_ID | Только серверная настройка личного чата владельца; пусто в .env.example |

Ни token, ни настоящий chat_id не зашиты в код, тесты, шаблон или документацию; не использовать NEXT_PUBLIC_. Endpoint фиксирован: HTTPS Telegram Bot API, метод sendMessage. Адрес API не берётся из формы/окружения; redirect запрещён. Токен входит в URL протокола Telegram: никогда не публиковать полный URL, сырые исключения/ответы или verbose сетевую диагностику.

Формат token/chat_id проверяется перед сетью; это не подтверждение действительности токена или получения сообщения. Отсутствие/невалидность настроек не закрывают форму и не меняют SMTP/API. В default конфигурации сеть Telegram вообще не вызывается.

## Одна команда настройки — позже, владельцем

Только **после отдельно разрешённого развёртывания этого PR**, в интерактивном SSH-терминале владельца файлов, с Node 24/npm/Python 3 в PATH:

```sh
cd /var/www/golwebstudio && npm run telegram:setup
```

Установщик `scripts/setup-telegram.py` сначала показывает область изменений и спрашивает `НАСТРОИТЬ`. Токен вводится скрыто через getpass; chat_id вводится интерактивно. Не передавать token аргументом, в shell history, чате или скриншоте. Токен агенту не нужен.

Меняются только три Telegram-ключа. Разбираются четыре Next production-профиля: `.env.production.local`, `.env.local`, `.env.production`, `.env`; другие строки, включая SMTP/LexRadar и многострочные значения, сохраняются. Telegram-ключи консолидируются в `.env.local`, флаг сначала false. Неоднозначный синтаксис, дубликаты/перекрытие ключа между источниками, inherited Telegram-переменные, tracked env, symlink/небезопасный владелец и конкурентная правка останавливают настройку, а не обходятся. Известные имена/безопасные статусы можно сообщить; значения и полные файлы публиковать нельзя.

Используются существующие SMTP helper-функции разбора/атомарной записи/отката, но SMTP configure/main не вызываются. Next loader проверяет точное сохранение Telegram-значений только в локальном subprocess stdin без печати значения, длины, хеша или фрагмента. Запись атомарна для каждого файла, с rollback при обычной ошибке и правами 600; backup с секретами не создаётся. Это не гарантия транзакции при отключении питания между несколькими файлами. Установщик не запускает PM2/Nginx, не меняет число процессов и не отправляет email.

### Контрольное сообщение и включение

1. После безопасного сохранения флаг остаётся false. Чтобы разрешить **одно** контрольное Telegram-сообщение, владелец отдельно вводит `ОТПРАВИТЬ`. Enter пропускает сеть и оставляет false.
2. Контрольный текст не утверждает SMTP acceptance и не отправляет письмо. `TELEGRAM_CONTROL_ACCEPTED` означает только HTTP/ok acceptance Telegram API, не прочтение владельцем.
3. Владелец проверяет свой личный чат. Только после фактического получения вводит `ПОЛУЧЕНО`; тогда установщик сохраняет true. Enter/ошибка/timeout оставляют false. Синтаксическая готовность сама по себе не включает уведомления.
4. Изменения окружения должен отдельно применить уполномоченный администратор к существующему процессу по [DEPLOYMENT](DEPLOYMENT.md). Установщик этого не делает; inherited PM2 variables могут иметь приоритет над файлом.
5. После отдельного разрешения на сквозную приёмку владелец может подтвердить связку обычной заявки и уведомления. В рамках разработки эта отправка не выполнялась.

## Диагностика без сообщений

Структура источников, без сети/изменений/вывода значений:

```sh
npm run telegram:setup -- --inspect
```

Эффективные enabled/ready через Next loader, тоже без сети/отправки:

```sh
npm run telegram:inspect
```

Первая команда проверяет дубликаты/унаследованные Telegram-ключи; вторая сообщает только флаг и синтаксическую готовность эффективной конфигурации. Вторая не доказывает отсутствие дубликатов. Включённый флаг не доказывает доставку.

Runtime сообщения журнала ограничены фиксированными кодами `TELEGRAM_NOTIFICATION_NOT_CONFIGURED`, `...INVALID_EVENT`, `...HTTP_ERROR`, `...API_ERROR`, `...INVALID_JSON`, `...NETWORK_ERROR`, `...TIMEOUT`. Не содержат URL, token, chat_id, UUID и данных заявки. `DISABLED`/`ACCEPTED` по умолчанию не засоряют runtime log. CLI печатает только фиксированные `TELEGRAM_ENABLED`/`DISABLED`, `CONFIG_READY`/`NOT_CONFIGURED`, `CONTROL_<status>` или общий `INSPECTION_FAILED`. Не требуются env dump или сырые ответы.

## Отключение только Telegram

В согласованном серверном источнике установить `TELEGRAM_NOTIFICATIONS_ENABLED=false` и отдельно штатно применить окружение к процессу. Если процесс переопределяет файл, сначала безопасно устранить конфликт источников без вывода значений. Не менять SMTP, LexRadar flags и другие строки, не запускать SMTP-установщик. Письма продолжают работать как прежде; для будущего повторного включения нужна отдельная приёмка.

## Ограничения надёжности

- Одна попытка, общий deadline **до 1500 ms** на fetch и JSON через AbortController и Promise.race; автоматических повторов нет. Этап ожидается обработчиком Next, не fire-and-forget.
- Ошибка, отсутствие настроек или timeout Telegram не меняют успешный SMTP/API ответ и не вызывают повтор письма. При SMTP failure/uncertain уведомления об успехе нет.
- При сбое сообщение может потеряться. Telegram мог принять запрос, но ответ потеряться: автоматический повтор создал бы риск дубля. Receipt API не подтверждает прочтение.
- SMTP acceptance не гарантирует поступление во входящие. Формулировка в уведомлении намеренно говорит только о принятии почтовым сервером.
- LexRadar делит SMTP+Telegram результат внутри существующего requestId cache 30 минут; тот же UUID/параллельный повтор не создаёт новое уведомление в этом окне и процессе. Рестарт/несколько workers/истечение TTL не дают exactly-once; сбой уведомления не перезапускается повтором UUID.
- Общая форма сохраняет прежний механизм повторов без новой idempotency: две отдельные принятые отправки могут дать два письма и два уведомления. Остальные выявленные аудитом дефекты этим PR не исправляются.

## Проверки разработки

Новые Node-тесты используют mock fetch/sender и синтетические identifiers: выключение/неполная конфигурация, HTTP/ok/JSON/network/timeout, отсутствие ПД/секретов в сообщении и диагностике, оба реальных обработчика, SMTP failure/uncertainty, неизменный успех при сбое Telegram, LexRadar concurrent/retry. Python unittest использует только temp fixtures и реальный локальный Next parser: сохранность SMTP/LexRadar, multiline, aliases/дубликаты, права/атомарность/rollback, concurrent edit, флаг false и owner receipt gating. Общий SMTP-service и diagnostics остаются без notification hook. Mock-тесты не подтверждают реальную доставку.
