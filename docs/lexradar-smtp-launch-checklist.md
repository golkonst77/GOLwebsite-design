# LexRadar: SMTP, proxy и включение

Форма по умолчанию закрыта. На 17.10.2026 реальная доставка не проверена: учётные данные SMTP и доступ к почтовому ящику не предоставлены. Unit/browser mocks не подтверждают доставку. В этой задаче production не меняется.

## Переменные (только окружение, никогда Git)

| Имя | Значение/назначение |
|---|---|
| YANDEX_EMAIL | Подтверждённый email отправителя Yandex |
| YANDEX_PASSWORD | Пароль приложения, не пароль входа |
| LEAD_TO_EMAIL | Один email получателя; fallback golwebstudio@mail.ru. На стенде — только контролируемый тестовый ящик |
| LEXRADAR_SITE_ORIGIN | Один публичный HTTPS origin, например https://www.golwebstudio.ru, без path/query; должен совпадать с фактическим каноническим доменом. http допускается только для localhost/loopback тестов |
| LEXRADAR_ABUSE_MODE | single-process или edge; без явного выбора форма закрыта |
| LEXRADAR_TRUST_PROXY | true только после проверки, что все запросы идут через доверенный proxy и прямой порт Node недоступен |
| LEXRADAR_CLIENT_IP_HEADER | x-real-ip для собственного proxy либо x-vercel-forwarded-for только при документированной гарантии платформы, что заголовок перезаписывается. Произвольные заголовки не принимаются |
| LEXRADAR_EDGE_RATE_LIMIT_CONFIRMED | true в режиме edge только после фактической настройки общего лимита на ingress |
| LEXRADAR_FORM_ENABLED | false/не задан до сквозного теста; true после теста на нужном окружении |

`single-process`: локальный limiter на процесс, 5 попыток / 10 минут. Без доверенного IP-заголовка все посетители делят общий bucket: это консервативный fallback, а не полноценная защита/масштабирование. Выбирать только для одного процесса с внешним ограничением тела/соединений. При добавлении workers/реплик перейти на edge, иначе каждый процесс имеет свой лимит.

`edge`: обязательны доверенный IP header и подтверждённый общий ingress limit. Переменная подтверждения сама ничего не настраивает и не доказывает защиту. Администратор должен проверить лимит между экземплярами и попытки обхода. Локальный limiter остаётся дополнительным барьером. X-Forwarded-For самим API игнорируется.

## Доверенная граница proxy

На собственном Nginx: закрыть прямой доступ к Node port, установить `proxy_set_header X-Real-IP $remote_addr;` (именно перезаписать), передавать правильные Host/X-Forwarded-Proto, ограничить `client_max_body_size 16k;`, `client_body_timeout 10s;`, число соединений и rate limit. Если перед Nginx есть CDN, настроить real_ip только для официальных доверенных CIDR; нельзя доверять XFF от любого клиента. Пример направления, не готовая конфигурация для слепого копирования: общая зона `limit_req_zone $binary_remote_addr zone=lexradar:10m rate=1r/m;` и `limit_req zone=lexradar burst=2 nodelay; limit_req_status 429;` на POST endpoint; применимость и пропускная способность проверяются администратором. При нескольких ingress зона памяти Nginx тоже не общая: нужен существующий общий edge/WAF limit либо единый ingress. Новый сервис здесь не добавляется.

На Vercel: не доверять произвольному первому XFF. До включения edge подтвердить поведение `x-vercel-forwarded-for` для конкретного deployment по текущей документации/тесту и настроить общий Firewall rate limit, включая прямой deployment URL, не только custom domain. Если гарантий нет, форму оставить выключенной. В serverless SMTP IPv6/порт 587 могут быть недоступны — проверяется `--verify` именно на целевом runtime. Конфигурация Vercel этой задачей не менялась.

Origin проверяется независимо от forwarded Host против LEXRADAR_SITE_ORIGIN, Sec-Fetch-Site=cross-site отклоняется. Это защита браузерного источника, не аутентификация: бот может отправить разрешённый Origin, поэтому требуются лимиты.

## Безопасная диагностика

```sh
npm ci
npm run smtp:diagnose
npm run smtp:diagnose -- --verify
```

Первая команда диагностики только сообщает boolean-флаги конфигурации, без адресов/секретов/соединений. `--verify` явно открывает SMTP/TLS и проверяет аутентификацию, но не отправляет писем и не доказывает доставку. Ошибки выводятся стабильным безопасным текстом. Учётные данные читаются обычным загрузчиком Next env. Не включать SMTP debug/logger и не публиковать .env/сырой ответ транспорта.

Transport сохранён: Yandex IPv6 `2a02:6b8::19d:587`, STARTTLS, TLS servername smtp.yandex.ru, проверка сертификата. Общая сессия ограничена 20 сек и transport закрывается. Принятие почтовым сервером определяется accepted/rejected, не просто fulfilled promise. После сетевого сбоя/таймаута доставка может быть неопределённой: это не успех и не гарантия, что письма не было.

## Сквозной тест на отдельном стенде

1. Проверить canonical domain/origin и proxy rules, установить только контролируемые SMTP/receiver credentials. Убедиться, что форма на production остаётся выключенной.
2. Выполнить typecheck/lint/tests/build, диагностику и `--verify`.
3. Временно включить LEXRADAR_FORM_ENABLED только на стенде; перезапустить процесс штатно, не печатая env.
4. Отправить одну заявку с пометкой TEST и собственным тестовым email; не использовать данные реальных клиентов. Проверить в ящике имя/URL/UTM/Reply-To/версию согласия/время и отсутствие рекламы.
5. Проверить Origin с внешним доменом, поддельный IP header с внешней стороны proxy и общий лимит между всеми репликами. Повторить UUID: в одном процессе должно быть одно письмо. Между процессами точно-однократная отправка НЕ гарантирована.
6. Проверить controlled SMTP rejection и отключение конфигурации: нет ложного успеха, поля сохраняются. После timeout/потерянного ответа UI блокирует повтор и предлагает уточнить статус по email.
7. Зафиксировать время, окружение, request ID и факт получения без паролей/содержимого персональных данных; очистить тестовые заявки согласно политике.
8. Только после правовой/визуальной приёмки и подтверждённой доставки владелец отдельно разрешает production публикацию/включение. Это задание такого разрешения не содержит.

## Восстановление после сбоя

Сначала выключить LEXRADAR_FORM_ENABLED штатной отдельной операцией администратора и проверить уведомление на странице/503 API. Проверить конфигурацию boolean-диагностикой, затем --verify. Не посылать автоматически повторные заявки после неопределённого результата: проверить ящик и согласовать повтор с заявителем.

Идемпотентность API: UUID + хеш payload, in-memory 30 минут, максимум 5000 записей/процесс; одинаковые конкурентные запросы делят результат, изменённый payload с тем же ID даёт 409. Перезапуск/другой экземпляр снимает эту гарантию. Сведения заявки не хранятся в отдельной БД; email остаётся существующим каналом. Для глобальной exactly-once потребовалось бы общее хранилище; оно не добавлено.
