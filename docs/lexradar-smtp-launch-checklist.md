# LexRadar: SMTP, proxy и включение

Форма по умолчанию закрыта. На 17.10.2026 реальная доставка не проверена: учётные данные SMTP и доступ к почтовому ящику не предоставлены. Unit/browser mocks не подтверждают доставку. В этой задаче production не меняется.

Актуальная production-инструкция для smtp.yandex.ru:465 и диагностики EAUTH: [Яндекс SMTP](./lexradar-yandex-production.md).

## Переменные (только окружение, никогда Git)

| Имя | Значение/назначение |
|---|---|
| SMTP_HOST | DNS-имя SMTP-провайдера, для production smtp.yandex.ru |
| SMTP_PORT | 465 (TLS) либо 587 (STARTTLS); по умолчанию 587 |
| SMTP_SECURE | true для TLS с начала соединения (465), false для обязательного STARTTLS (587); если отсутствует, определяется по порту |
| SMTP_USER | Логин SMTP, для production golkonst@yandex.ru |
| SMTP_PASS / SMTP_PASSWORD | Пароль приложения SMTP (совместимые имена, конфликт блокирует отправку); только в secret env/.env.local с правами 600 |
| SMTP_FROM | Разрешённый провайдером адрес отправителя; по умолчанию SMTP_USER, если это email |
| YANDEX_EMAIL | Старый email Yandex; используется только при полном отсутствии всех SMTP_* |
| YANDEX_PASSWORD | Старый пароль приложения Yandex; используется только при полном отсутствии всех SMTP_* |
| MAIL_TO / LEAD_TO_EMAIL | Один email получателя (конфликт имён блокирует отправку); fallback golwebstudio@mail.ru. На стенде — только контролируемый тестовый ящик |
| LEXRADAR_SITE_ORIGIN | Один публичный HTTPS origin, например https://www.golwebstudio.ru, без path/query; должен совпадать с фактическим каноническим доменом. http допускается только для localhost/loopback тестов |
| LEXRADAR_ABUSE_MODE | single-process или edge; без явного выбора форма закрыта |
| LEXRADAR_TRUST_PROXY | true только после проверки, что все запросы идут через доверенный proxy и прямой порт Node недоступен |
| LEXRADAR_CLIENT_IP_HEADER | x-real-ip для собственного proxy либо x-vercel-forwarded-for только при документированной гарантии платформы, что заголовок перезаписывается. Произвольные заголовки не принимаются |
| LEXRADAR_EDGE_RATE_LIMIT_CONFIRMED | true в режиме edge только после фактической настройки общего лимита на ingress |
| LEXRADAR_FORM_ENABLED | false/не задан до сквозного теста; true после теста на нужном окружении |

`single-process`: локальный limiter на процесс, 5 попыток / 10 минут. Без доверенного IP-заголовка все посетители делят общий bucket: это консервативный fallback, а не полноценная защита/масштабирование. Выбирать только для одного процесса с внешним ограничением тела/соединений. При добавлении workers/реплик перейти на edge, иначе каждый процесс имеет свой лимит.

`edge`: обязательны доверенный IP header и подтверждённый общий ingress limit. Переменная подтверждения сама ничего не настраивает и не доказывает защиту. Администратор должен проверить лимит между экземплярами и попытки обхода. Локальный limiter остаётся дополнительным барьером. X-Forwarded-For самим API игнорируется.

## Доверенная граница proxy

На собственном Nginx: закрыть прямой доступ к Node port, установить `proxy_set_header X-Real-IP $remote_addr;` (именно перезаписать), передавать правильные Host/X-Forwarded-Proto, ограничить `client_max_body_size 16k;`, `client_body_timeout 10s;`, число соединений и rate limit. Если перед Nginx есть CDN, настроить real_ip только для официальных доверенных CIDR; нельзя доверять XFF от любого клиента. Пример направления, не готовая конфигурация для слепого копирования: общая зона `limit_req_zone $binary_remote_addr zone=lexradar:10m rate=1r/m;` и `limit_req zone=lexradar burst=2 nodelay; limit_req_status 429;` на POST endpoint; применимость и пропускная способность проверяются администратором. При нескольких ingress зона памяти Nginx тоже не общая: нужен существующий общий edge/WAF limit либо единый ingress. Новый сервис здесь не добавляется.

На Vercel: не доверять произвольному первому XFF. До включения edge подтвердить поведение `x-vercel-forwarded-for` для конкретного deployment по текущей документации/тесту и настроить общий Firewall rate limit, включая прямой deployment URL, не только custom domain. Если гарантий нет, форму оставить выключенной. В serverless SMTP IPv6/порт 587 могут быть недоступны — проверяется `--verify` именно на целевом runtime. Конфигурация Vercel этой задачей не менялась.

Origin проверяется независимо от forwarded Host против LEXRADAR_SITE_ORIGIN, Sec-Fetch-Site=cross-site отклоняется. Это защита браузерного источника, не аутентификация: бот может отправить разрешённый Origin, поэтому требуются лимиты.

## Безопасная диагностика

```sh
npm ci
npm run smtp:diagnose
npm run smtp:diagnose -- --verify
```

Первая команда диагностики сообщает безопасные статусы переменных, источники, дубликаты, перекрытия и конфликты, без значений и соединений. `--verify` явно открывает SMTP/TLS и проверяет аутентификацию, но не отправляет писем и не доказывает доставку. Ошибки выводятся стабильным безопасным текстом. Учётные данные читаются обычным загрузчиком Next env. Не включать SMTP debug/logger и не публиковать .env/сырой ответ транспорта.

При отсутствии всех SMTP_* сохранён прежний транспорт Yandex IPv6 `2a02:6b8::19d:587` с STARTTLS и servername smtp.yandex.ru. При наличии любой SMTP_* требуется полная универсальная конфигурация; смешивание учётных данных провайдеров запрещено. Универсальный транспорт использует SMTP_HOST для DNS и TLS/SNI, требует TLS не ниже 1.2 с проверкой сертификата. SMTP_FROM должен быть разрешён провайдером. Пароль передаётся без удаления значимых пробелов.

Общая сессия ограничена 20 сек, transport закрывается. Успех — только после завершения sendMail с нужным получателем в accepted и без rejected. Ошибка или неопределённый результат никогда не показываются как успех. Подтверждение SMTP не доказывает попадание во входящие.

## Настройка сервера и реальная тестовая отправка

1. На сервере в каталоге проекта сохранить SMTP_* из .env.example в .env.local (chmod 600) либо в secret environment службы. Для Яндекса: smtp.yandex.ru, порт 465, SMTP_SECURE=true, логин и отправитель golkonst@yandex.ru, SMTP_PASS — пароль приложения этого аккаунта. Проверьте актуальные реквизиты в настройках почтового провайдера. Не сохранять секреты в Git/PR, не использовать NEXT_PUBLIC_*.
2. Задать MAIL_TO=golwebstudio@mail.ru (или прежнее имя LEAD_TO_EMAIL без конфликта). Оставить LEXRADAR_FORM_ENABLED=false на production. Установить LEXRADAR_SITE_ORIGIN в фактический origin страницы после редиректа и настроить защиту proxy по разделу выше.
3. С целевого сервера проверить доступность исходящего TCP-порта SMTP и DNS, выполнить npm ci, npm run check, npm run smtp:diagnose и npm run smtp:diagnose -- --verify. Команда verify не отправляет письмо.
4. Для одного реального синтетического письма выполнить `npm run smtp:diagnose -- --production-test`. Она проверяет дубликаты и цель, соединение TLS, SMTP-авторизацию, затем вызывает существующий sendEmail ровно один раз; печатает безопасные статусы/коды и Test ID, не меняет флаг формы. Успех означает приём SMTP-сервером; отдельно найти письмо с этим ID в ящике golwebstudio@mail.ru (включая спам). После неопределённого результата сначала проверить ящик, не повторять вслепую.
5. После подтверждённого теста SMTP выполнить сквозной тест формы на отдельном стенде по следующему разделу. Только после успешных проверок включить LEXRADAR_FORM_ENABLED=true на production и перезапустить службу (например, pm2 restart golwebstudio --update-env). Не включать форму только на основании наличия переменных, unit-тестов или verify.
6. При любом сбое вернуть LEXRADAR_FORM_ENABLED=false и перезапустить службу: форма покажет альтернативный email, API вернёт 503 без отправки.

LexRadar использует /api/lexradar и существующие lib/lexradar-handler.ts / lib/email-service.ts. /api/lead — общая форма сайта с другим контрактом (телефон обязателен); переносить туда поля LexRadar не требуется. Автоматический аудит не вызывается. Дизайн, политика и ссылка согласия сохраняются.

## Сквозной тест на отдельном стенде

1. Проверить canonical domain/origin и proxy rules, установить только контролируемые SMTP/receiver credentials. Убедиться, что форма на production остаётся выключенной.
2. Выполнить typecheck/lint/tests/build, диагностику и `--verify`.
3. Временно включить LEXRADAR_FORM_ENABLED только на стенде; перезапустить процесс штатно, не печатая env.
4. Отправить одну заявку с пометкой TEST и собственным тестовым email; не использовать данные реальных клиентов. Проверить в ящике имя/URL/UTM/Reply-To/версию согласия/время и отсутствие рекламы.
5. Проверить Origin с внешним доменом, поддельный IP header с внешней стороны proxy и общий лимит между всеми репликами. Повторить UUID: в одном процессе должно быть одно письмо. Между процессами точно-однократная отправка НЕ гарантирована.
6. Проверить controlled SMTP rejection и отключение конфигурации: нет ложного успеха, поля сохраняются. После timeout/потерянного ответа UI блокирует повтор и предлагает уточнить статус по email.
7. Зафиксировать время, окружение, request ID и факт получения без паролей/содержимого персональных данных; очистить тестовые заявки согласно политике.
8. Включать production только после подтверждённого SMTP-теста, получения контрольного письма и сквозных проверок. В этом PR production-флаг не включается: реквизиты SMTP и доступ к серверу/ящику в среде отсутствуют.

## Восстановление после сбоя

Сначала выключить LEXRADAR_FORM_ENABLED штатной отдельной операцией администратора и проверить уведомление на странице/503 API. Проверить конфигурацию безопасной диагностикой, затем --verify. Не посылать автоматически повторные заявки после неопределённого результата: проверить ящик и согласовать повтор с заявителем.

Идемпотентность API: UUID + хеш payload, in-memory 30 минут, максимум 5000 записей/процесс; одинаковые конкурентные запросы делят результат, изменённый payload с тем же ID даёт 409. Перезапуск/другой экземпляр снимает эту гарантию. Сведения заявки не хранятся в отдельной БД; email остаётся существующим каналом. Для глобальной exactly-once потребовалось бы общее хранилище; оно не добавлено.

На целевом runtime функция/ingress должны позволять не менее 40 секунд обработки POST (чтение до 10 сек + SMTP до 20 сек + запас). Это нужно проверить по текущему тарифу/настройкам платформы, не меняя production в рамках этой задачи. Ограничения serverless duration/IPv6 и общий ingress limit остаются проверкой администратора.
