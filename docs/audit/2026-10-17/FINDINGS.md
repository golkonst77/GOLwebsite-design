## APP-01 — Общая форма не проверяет Origin и Content-Type

**Серьёзность:** средняя. **Категория:** защита приложения. **Статус:** подтверждено, открыто; код не исправлялся.

**Место:** [app/api/lead/route.ts#L255](https://github.com/golkonst77/GOLwebsite-design/blob/e8c85f52edaa9c6e51d63f14a654a55a14fa1851/app/api/lead/route.ts#L255).

**Ожидаемое:** Отклонить cross-site/simple text/plain запрос до отправки; не переносить защиту LexRadar на другой endpoint по предположению.

**Фактическое:** Обработчик сразу читает request.json, не сравнивает Origin/Sec-Fetch-Site и не требует JSON Content-Type.

**Воспроизведение / доказательство:** E1: foreign Origin + cross-site + text/plain с валидным JSON → 200, 1 mock send. См. [EVIDENCE](EVIDENCE.md).

**Рекомендация для отдельной задачи:** Отдельная задача: определить origin/JSON policy общей формы и добавить соответствующие проверки/регрессии.

**Ограничения:** Подтверждено для обработчика; настоящий CORS/Nginx/WAF и production-запросы не проверялись. Origin не заменяет антибот-защиту и не защищает от подделки заголовка небраузерным клиентом.

## APP-03 — Лимит общей формы допускает параллельные отправки и доверяет первому XFF

**Серьёзность:** высокая. **Категория:** защита приложения. **Статус:** подтверждено, открыто; код не исправлялся.

**Место:** [app/api/lead/route.ts#L294](https://github.com/golkonst77/GOLwebsite-design/blob/e8c85f52edaa9c6e51d63f14a654a55a14fa1851/app/api/lead/route.ts#L294).

**Ожидаемое:** Лимит 3 отправок/10 минут должен резервировать попытку до SMTP await и использовать доказанный источник IP.

**Фактическое:** Счётчик растёт только после успешного sendEmail (строка 327). Первый XFF берётся без настройки доверия (строка 28). Ошибки/параллельные запросы не занимают слот до отправки.

**Воспроизведение / доказательство:** E1: последовательные 5 одного IP → 200/200/200/429/429 и 3 mock send; параллельные 5 → все 200 и 5 send; пять разных XFF → пять send. См. [EVIDENCE](EVIDENCE.md).

**Рекомендация для отдельной задачи:** Отдельная задача для общей формы: atomic reservation/лимит попыток, ограниченная ёмкость и явная доверенная proxy-граница.

**Ограничения:** Параллельный обход подтверждён локально. Подмена XFF эксплуатируема только если ingress не перезаписывает его; production proxy неизвестен. Высокий приоритет из-за потенциального массового SMTP abuse; реальная атака не проводилась.

## Неподтверждённые проблемы и решения владельца

### OBS-01 — локальная производительность и SEO

Средняя важность, **вероятно требует исследования**, не подтверждённый production-дефект. E5: один mobile Lighthouse run главной дал Perf=80, LCP=3.7 s, CLS=.19, image estimate 96 KiB. next.config.mjs:4 задаёт unoptimized images; причина CLS отдельно не доказана. Рекомендация: после приёмки повторить стабильные локальные измерения/trace, согласовать budgets и лишь затем ставить задачу. Ограничения: loopback, один прогон, simulated CPU/network, без CrUX. Отсутствие canonical/OG на главной подтверждено, но необходимость дополнений — продуктовая SEO-задача, не сломанная ссылка.

### OBS-02 — контакты, обещания и юридические процессы

Низкая важность контентного решения; **корректность не проверена**. footer.tsx:21/:94 содержит @gol_studio и hello@gol.studio; FinalCTA использует @teodor77 и golwebstudio@bk.ru. Это подтверждённое различие, но не доказанная неработоспособность контактов. solution.tsx:12/:30 содержит +45% конверсии и 100% гарантию; подтверждений в коде нет, их подлинность по репозиторию не устанавливается. Политика описывает третьих лиц/трансграничность, реальный маршрут аналитики не исследован. Владелец выбирает основные контакты, подтверждает маркетинговые доказательства и передаёт правовые тексты юристу. Не менять значения по догадке.

### OBS-03 — production/GitHub и оставшиеся PR

Средняя операционная важность, **не проверено**: соответствие Ubuntu/PM2/Nginx source/build/environment GitHub SHA, реальные ingress limits, доставляемость/retention/mailbox access. Доставка подтверждена владельцем, новых SMTP-проверок нет. Подготовлена read-only Git-команда в CONFIGURATION; владелец решает, выполнять ли её и как отдельно сверять запущенный build. Открытые #1/#5 содержат прежние альтернативные изменения; решить их судьбу отдельно, не объединять автоматически с аудитом.
