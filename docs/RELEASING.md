# Выпуск версии

1. Начать от актуального main, проверить предыдущие теги/релизы и выбрать свободную semver-версию.
2. Согласовать package.json, корневой version и packages[""].version в package-lock.json, CHANGELOG и текущую документацию. Не менять номера в архивных отчётах: они описывают старые коммиты.
3. Выполнить npm run check и npm run test:browser. Не использовать реальные SMTP credentials; не отправлять письма. Проверить diff и отсутствие env/backup/log/данных заявителей.
4. Создать PR к main. Перед merge проверить CI на точном head SHA, включая успешные Vercel checks, если они обязательны. Не обходить rulesets, обязательные approvals или checks, не делать force push.
5. После merge workflow Check повторяет проверки точного main SHA. Задание publish-release выполняется только после check и только для выпуска 1.3.1. Оно использует GITHUB_TOKEN с contents:write только в этом задании, создаёт тег и GitHub Release на точном GITHUB_SHA, берёт текст из `docs/releases/1.3.1.md` и не обращается к VPS/SMTP. Старый тег не передвигается. Последующие push после существующего релиза не публикуют его заново.
6. Проверить фактическое наличие Release и соответствие target/tag коммиту. Если GitHub запретил публикацию, workflow не является успешным релизом. Администратор должен устранить ограничение или опубликовать через штатный GitHub UI на проверенном merge SHA. Не менять настройки прав автоматически.

Этот выпуск не меняет приложение, за исключением номера версии; он фиксирует предыдущие изменения и документацию. Release не является резервной копией env или доказательством точного состава production. Установка на production выполняется отдельно с разрешения и по DEPLOYMENT.

Для следующей версии обновить CHANGELOG/notes и явно адаптировать условие publish-release; текущий job ограничен 1.3.1, чтобы не создавать новые релизы без отдельного намерения владельца.
