# Развёртывание, сверка и восстановление

Использовать npm и Node 24; старый Windows BAT-деплой с pnpm/reset --hard не применять. Эта инструкция не разрешает менять production: требуется отдельное согласование. GitHub Release не устанавливается на VPS автоматически этой процедурой.

## Сверка production без изменений

Выполнить в SSH-терминале сервера:

```sh
cd /var/www/golwebstudio &&
GIT_OPTIONAL_LOCKS=0 git rev-parse HEAD &&
GIT_OPTIONAL_LOCKS=0 git rev-parse --abbrev-ref HEAD &&
GIT_OPTIONAL_LOCKS=0 git -c core.quotePath=true diff --name-only HEAD &&
GIT_OPTIONAL_LOCKS=0 git -c core.quotePath=true ls-files --others --exclude-standard
```

Вывод: SHA, ветка, затем только имена изменённых/неотслеживаемых файлов. Игнорируемые env-файлы не читаются. При detached HEAD строка ветки будет HEAD. Команда не делает fetch/checkout/build/restart и не выводит содержимое файлов. Отсутствие списка изменений подтверждает чистоту отслеживаемого кода, но не идентичность секретов, ignored-файлов или запущенного build. Если SHA отличается, сравнить точные коммиты на GitHub.

Если есть изменения исходников, остановить обновление: сохранить и проверить именно эти файлы в отдельной ветке/PR. Не добавлять секреты, env-backup, логи или данные заявок. Не использовать git add . вслепую. GitHub-копия не заменяет защищённую серверную резервную копию.

## Перед отдельно разрешённым обновлением

1. Зафиксировать предыдущий SHA, версию и команду запуска службы. Подтвердить чистоту исходников; изменения нельзя стирать.
2. Сохранить конфигурацию и секреты в существующем защищённом хранилище администратора вне Git/публичных архивов. Не копировать env в backup внутри репозитория.
3. Выбрать точный проверенный SHA main/релиза, подготовить окно обслуживания и откат. Сборка поверх .next живого процесса может повлиять на сайт; предпочтителен отдельный release-каталог по принятой администратором процедуре. Не менять схему размещения наугад.
4. В согласованном checkout: `npm ci`, `npm run check`, при необходимости браузерная проверка. Явно использовать Node 24 в PATH; не смешивать менеджеры пакетов.
5. Сохранить рабочее серверное окружение. Новые установки должны оставаться с выключенной формой до приёмки. SMTP-установщик не является обязательным шагом каждого выпуска.
6. Только при успешной сборке штатно переключить подготовленный релиз и перезапустить существующее приложение PM2. Не менять число процессов, proxy и Nginx без необходимости.
7. Проверить HTTP главной, /lexradar, /privacy и /lexradar/consent, статус PM2 и версию/commit build. Не отправлять письмо ради каждого документационного релиза.

Команда перезапуска существующего приложения после разрешённого изменения конфигурации: `pm2 restart golwebstudio --update-env`. Она не гарантирует очистку старых унаследованных переменных; источник окружения службы проверяется отдельно без публикации значений.

## Откат

Использовать записанный предыдущий SHA и защищённую конфигурацию. В чистом согласованном release-checkout восстановить именно этот коммит, выполнить npm ci и успешный production build, затем штатно переключить приложение/перезапустить. Не применять reset --hard к неизвестным локальным правкам и не удалять env. При неопределённой доставке сначала проверить ящик и идентификатор заявки, а не повторять отправки.

Тег указывает на исходники, но не содержит env, зависимости node_modules и .next; для восстановления необходимы lockfile, Node 24 и безопасно сохранённое серверное окружение.
